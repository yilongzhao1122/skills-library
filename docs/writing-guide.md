# 功能说明的写法

读者应该能从说明中判断：这个技能解决哪件事，需要准备什么，以及完成后会拿到哪些结果。

## 先讲功能和原理

开头用一段话说明使用场景和交付结果，随后解释关键步骤之间的关系。例如，AutoDL（云计算平台）部署技能通过 PC（个人电脑）建立 SSH（安全远程连接协议）反向隧道，让远端指定程序使用电脑上的认证代理；Codex（编程助手）的外层代理入口和官方管理的内部程序分开保存，使升级后的程序继续使用同一条联网路径。

能力范围用能完成的工作来表达。准备条件写成行动步骤，结果说明写清观察对象和判断依据。

例如：“四个网站的请求结果记录了网络出口、响应状态和证书校验情况；模型回答验证了当前账号到模型服务的请求路径。”

## 英文词紧接中文解释

每篇可以独立阅读的文档，首次出现专业英文词或缩写时，紧接一个中文括号解释。例如：

- GOST（网络代理转发工具）。
- WireGuard（虚拟专用网络协议）。
- PTY（伪终端，用来模拟真实终端交互）。
- `CODEX_HOME`（Codex 状态与配置目录）。

GitHub、Git、ChatGPT、Python、Windows、Linux、IP 等常用名称可直接使用。专业品牌名称在首次出现时补充其用途。代码中的命令、路径、配置键保持原样，在相邻正文介绍含义。

## 用 Humanizer 润色

Humanizer（文字润色技能）的来源是 [blader/humanizer](https://github.com/blader/humanizer)，[执行说明](https://github.com/blader/humanizer/blob/main/SKILL.md)随上游维护。

功能介绍、工作原理、技能选择描述和更新说明都按以下顺序审阅：

1. 通读全文，标出夸张评价、重复铺垫、机械列举、口号式结尾和多余的转折。
2. 按读者要完成的任务重写，把动作和作用放在一起说清楚。
3. 核对功能、数字、日期、版本和命令，保留原有事实。
4. 再读一遍，删去重复内容，调整句子的长短和段落衔接。

技术说明保持朴素、具体。比如“脚本记录本实例的进程身份，停止时逐项核对”，已经解释了机制和作用。文档直接保留这样的事实。

## 记录实测结果

注明测试日期、环境、实际执行的检查、观察值和交付状态。区分本轮执行的检查与已保存的历史记录，让读者知道每项结果来自哪次操作。

公开案例保存版本、状态码、出口一致性和预期回答等验证信息。实例地址、个人网络地址、账号信息与凭据保存在本地私密记录中。示例参数使用用途明确的占位符，部署时通过调查填写。
